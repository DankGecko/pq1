# Formal-verification soundness roadmap (2026-06)

**Purpose.** Push PQSigner's formal verification as hard as is realistically achievable, so a green checkmark *means something* and never degrades to "maybe it works." Derived from a wide-net deep-research pass (8 parallel primary-source angles) cross-mapped onto the project's actual FV stack and the soundness residuals the 2026-06 EF-swarm audit surfaced. Companion to `lean-verification-research-2026-06.md`, `spec-assurance-research-2026-06.md`, `security-tooling-sota-2026-06.md`.

> **Scope honesty up front (the thesis of this doc).** No end-to-end ∀ guarantee over the *shipped device* exists or is achievable: A1/keccak/A5 bottom out on hash conjectures + consensus facts, the multi-tool composition is human-glued, and the Charon/EVM-semantics fidelity is assumed. The goal is therefore **not** "prove everything" — it is to (a) make every theorem *non-vacuous* and *say what it claims*, (b) close the residuals that genuinely *can* be closed to a ∀, and (c) state the irreducible ceilings as honest, auditable cited-TCB rather than hiding them behind an overclaimed "verified."

---

## 0. The one cross-cutting finding (every research angle hit it independently)

**`#print axioms` / no-`sorryAx` is GREEN precisely on the vacuous conjuncts.** Kernel-clean ≠ non-trivial. A theorem `∀x, P x → Q x` with an *unsatisfiable* `P`, or a conjunct whose predicate never fires, adds **zero** axioms to the print and passes every gate the project currently runs. This is exactly the EF audit's `entrypoint_honest` tautology (P2), the all-zero stub signer's unsatisfiable round-trip predicate (P9), and the non-operational EUF-CMA conjunct (P9). It is a *named, classical* failure mode:

- **Vacuity detection / "interesting witness"** — Kupferman–Vardi (STTT 2003, https://link.springer.com/article/10.1007/s100090100062); Beer et al. (FMSD, https://www.cs.toronto.edu/~chechik/courses05/csc2108/beer01.pdf). A property that holds without exercising its antecedent is vacuous; the fix is a witness that *exercises* it.
- **Certora `rule_sanity`** ships an automated `vacuity` + `assert_tautology` check for exactly this (https://docs.certora.com/en/latest/docs/prover/checking/sanity.html). Lean has no built-in equivalent → it must be a written discipline + CI lemma.
- **The hax structural-gaps audit (eprint 2026/670)** names "specification gaming" (admit/assume/unsatisfiable-precondition conjuncts that typecheck clean) as a distinct exploit class against a sibling Rust→proof pipeline. *[2026 paper, verify; the underlying idea is old and the mapping is exact.]*

**The EF remediation fixed these three by doc-honesty. This roadmap's Tier-0 upgrades them from honest docstrings to kernel-enforced non-vacuity** — the difference between "we noticed three vacuous axioms" and "vacuity can't reach `master` again."

## 2. Prioritized "do this next" sequence

### Tier 0 — this sprint · cheap · converts luck→kernel-facts + closes the one genuinely-closable ∀

**T0.1 — Anti-vacuity CI gate (highest leverage, days).** For every cited axiom and every security predicate, add to the Lean tree + CI:
- a **satisfiability/witness lemma** — `∃` a reachable state where each conditional axiom's hypothesis is *true* and one where it is *false* (proves the hypothesis is contingent, not `True`); for `entrypoint_honest` this kills the tautology as a *kernel* fact, not a docstring.
- a **refutation theorem** — exhibit a concrete forgery and prove the EUF-CMA forgery predicate *fires* on it (`∃ m, signable m ∧ isForgery …`); exhibit a real-signer honest signature and prove the round-trip predicate is *satisfiable* (kills the stub-signer vacuity). The all-zero stub must be replaced by — or witnessed against — the actual C10 `Sign` for ≥1 concrete keypair.
- **`Plausible` smoke tests** (Lean core) on the round-trip + forgery predicates — fastest way to *catch the next* vacuity before it ships.
- a **spec-mutation harness** — script that comments out each axiom/conjunct and re-`lake build`s, *expecting failure*; a still-green build means the conjunct is dead.
- **banned-tactic CI grep** — ban `native_decide`, `decide +native`, `Lean.ofReduceBool`, `@[csimp]`, and audit every `implemented_by`/`@[extern]` in the Aeneas-extracted cone. `#print axioms` is bypassable through these (lean4 issue #7463, https://github.com/leanprover/lean4/issues/7463) and they are exactly your opaque-SHA extern + extraction-shim TCB (Lean ref: https://lean-lang.org/doc/reference/latest/ValidatingProofs/).

**T0.2 — Discharge `hInv` as a real inductive invariant (the *one* residual cleanly closable to a genuine ∀).** `hInv` (`slotUses[i] + offchainSigCount[i] < MAX_SLOT_USES`) lives in **decidable integer arithmetic**, so uninterpreted SHA-256 is here both *sound and complete* — it does **not** inherit the A3.1 ceiling. Foundry fuzzing is the wrong *shape* (the reachability diameter is ~65 536 transitions; bounded search structurally cannot certify it). Replace with the inductive method: **base** (init/`createAccount` seeds `local=last=0` ⊨ `hInv`) + **single-transaction all-methods preservation** from a *fully symbolic* pre-state assuming `hInv` (`hInv → hInv'` after any one counter-writing selector). Then the n-step induction is a one-liner. Discipline (do NOT relocate the transcription TCB): prove `hInv` *in the same layer as the theorem that consumes it*.
- The EF **P3** fix already added the cross-counter preservation lemmas (`setOffchain/bumpSlot/bumpBootstrap_preserves_*`) — they are the building blocks. Assemble a `Reachable σ → hInv σ` theorem and thread it to replace the free `hInv` hypothesis with a `Reachable` hypothesis (do **not** make the theorem unconditional — off-cap the bytecode reverts with no characterizing axiom; the EF P1 adversary flagged this).
- **Method-completeness is the soundness crux**: enumerate *every* writer of those counters (Type-2 bump, `executeWithOffchainCount`, Type-1 (re)install, admin-wipe/factory-reset) — a hand-omitted writer is a green-but-unsound ∀. Bytecode-level all-methods (Certora `invariant`+`requireInvariant`, or Kontrol over real selectors) is strictly safer than a hand list.
- The bugs the inductive step will surface that depth-2 fuzzing cannot: the **strict-`<` vs `+1` boundary** (`sum = MAX−1` → `+1` → violates `<`, ~65 535 calls from genesis), and a **symbolic `newOffchainCount`** check-ordering edge.
- Layer choice: cheapest to *find* the strengthening = **Apalache** (TLA+, ~50 LOC, hours — https://apalache-mc.org, arXiv:2205.06360); discharge for real via **Kontrol/Halmos `setArbitraryStorage` single-tx preservation** over the deployed bytecode (closes it against the real EVM), **Certora `invariant`** (turnkey, Prover-in-TCB), or **Veil** (auto-active transition-system verification *embedded in Lean 4*, CAV'25 — https://veil.dev, https://github.com/verse-lab/veil) if staying kernel-native over the model.

### Tier 1 — weeks · high-value

**T1.1 — A5 quantitative floor (days–weeks, no new tooling, the highest-value crypto item).** The reduction *shape* is published and machine-checked **for standardized SPHINCS+** (Barbosa–Dupressoir–Hülsing–Meijers–Strub, "A Tight Security Proof for SPHINCS+, Formally Verified," ASIACRYPT 2024, https://eprint.iacr.org/2024/910), but **C10's +C target-sum compression is outside the entire mechanized corpus** and there is **no public bit-security number for C10**. Two concrete actions: (1) plug C10's `(h=18,d=2,a=11,k=13,w=8, q=2^16 per-chain cap)` into the published HK/Framework bound (https://eprint.iacr.org/2022/346) with the **+C-modified ITSR term** (the FORS term is where all three C10 deviations intersect; eprint 2022/778) → a concrete `Adv ≤ ε` floor + defensible max-signatures budget; (2) **diff the project's Lean reduction against the post-2022 HK structure** (M-EUF-GCMA of FORS-TW + WOTS-TW SM-TCR + hypertree, with **SM-DSPR not single-target PRE**) to confirm it isn't re-implementing the historical ~40-bit flaw. Do **not** attempt a fresh EasyCrypt/SSProve mechanization of +C — that is a flagship-paper, multi-person-year effort. *Confirm "C10 = SPHINCS+C instance" against the firmware index encoding first — it is an inference (from `target_sum=205` + 4008 B sig), load-bearing for the above.*

**T1.2 — De-bald A1 (SHA-256), keep it quarantined from A5.** Port Appel's Coq FIPS-180-4 SHA-256 spec (TOPLAS 2015, https://www.cs.princeton.edu/~appel/papers/verif-sha-2.pdf — a proof-assistant spec, easier to re-express in Lean than HACL\*'s F\*) into Lean as a reference; prove **one quarantined lemma** `opaque_sha256 ≡ FIPS_spec` used *only* on the verifier-roundtrip + KAT path, **never** imported into the A5 reduction (A1/A5 tension: A5 *requires* SHA opaque). CI-cross-check the spec against the **NIST CAVP** KAT corpus. This shrinks A1 from "uninterpreted oracle" to "an auditable ~70-line spec that faithfully transcribes FIPS English" — strictly better, never zero.

**T1.3 — Harden the Rust→Lean (Aeneas/Charon) extraction gate (low-moderate).** Two independent layers (regeneration-diff alone cannot catch a *consistently-wrong* translation): (i) CI regenerates Charon+Aeneas from source and `git diff --exit-code` (the layer whose absence let stale LLBC through, EF P4); (ii) **differential KAT `#eval`** of the extracted Lean vs the shipped Rust on shared vectors (the only layer that catches consistent mistranslation); (iii) pin Charon/Aeneas/Lean/Mathlib toolchain versions. Aeneas's borrow-checking *is* proven sound (ICFP 2024, https://dl.acm.org/doi/10.1145/3674640) so the TCB legitimately shrinks to **rustc-MIR + Charon LLBC-faithfulness** (Charon has *no* foundational soundness proof — https://arxiv.org/html/2410.18042v1; state it). For the unsafe sites outside Aeneas's sound fragment (FI volatiles, `static mut`, CMSE veneers, NS-ptr): add **Kani** BMC (cheap, exhaustive-within-bound, UB net — https://model-checking.github.io/kani/) now; reserve **RefinedRust** (foundational, Iris, costly) or **Verus** (SMT, cheaper) for the 2–3 highest-value unsafe invariants only.

### Tier 2 — larger · the real ∀ push on A3.1

**T2.1 — A3.1 is NOT a fundamental ceiling; close it compositionally.** Under uninterpreted SHA-256 + C10's **statically-bounded loops** (all params compile-time constants, no input-dependent iteration), "deployed bytecode ≡ spec, ∀ signatures" is a **decidable QF_ABV+EUF query** via congruence closure — the obstacle is SMT term/path *explosion*, not a theory wall, and not loop-unsoundness. The viable shape is **per-primitive** (WOTS-chain / FORS / Merkle / hypertree-layer), mirroring the existing Lean sub-lemma structure and the A3.1 interpreter-refinement build already underway (`execC10Asm = Spec.verify`). Existence proof it's reachable: the **KEVM Eth2-deposit-contract proof** verified *compiled bytecode* ≡ spec and found 4 Vyper compiler bugs (https://link.springer.com/chapter/10.1007/978-3-030-53288-8_8).
- **Kernel rung (the real one, continue building it):** the SphincsCVerify interpreter-refinement is the *only* path binding deployed bytecode directly to the Lean spec with no trusted reference; its irreducible TCB collapses to the Lean EVM-semantics fidelity (= A4). Evaluate **EVMYulLean** (Nethermind, an executable EVM+Yul model *in Lean 4* — https://github.com/NethermindEth/EVMYulLean) as the trust-base-minimal long game (pre-release; lacks gas model + some opcodes, but a pure-computation verifier sidesteps most gaps).
- **Cheap complementary ∀-rung today:** `hevm equivalence` or Halmos `check_*` proving deployed `SPHINCsC10Asm` ≡ a reference verifier, reusing the project's **existing PQ1 `f_sha256` uninterpreted-precompile patch** (already in the local halmos fork, `sevm.py` PQ1 patch), **injectivity DISABLED (congruence-only)** so the ∀ holds for *every* interpretation of SHA-256, full loop-unroll to the C10 static max, asserting **zero partial-exploration warnings**. This only *shifts* trust to `reference ≡ Lean spec` — but it's a real ∀-over-calldata bytecode guard against optimizer/codegen drift, days not weeks.
- Label the KAT corpus + 250-mutant differential explicitly as **harness-sensitivity** evidence, never ∀-coverage.

**T2.2 — Shrink the LeanModel.sol↔Lean transcription TCB.** Codegen the bridge from the Lean model (single source of truth, extending the `xtask gen-solidity-constants`/`PqsignerProto` pattern) + cross-execute a shared corpus through both. Kontrol/KEVM already retires the hand-transcription for the *control-flow* bridge axioms (independent KEVM engine, no `LeanModel.sol` mirror) — lean on that.

### Tier 3 — the honest assurance case (communication, cross-cutting, ongoing)

**T3.1 — One auditor-facing artifact.** A seL4-style "What the Proofs Assume" TCB ledger (https://sel4.systems/Verification/assumptions.html) + EverCrypt-style published-TCB list (https://project-everest.github.io/assets/evercrypt.pdf) + a **GSN / Assurance-2.0** case (OMG SACM https://www.omg.org/spec/SACM/; eliminative argumentation https://arxiv.org/abs/2405.15800) whose top claim (`theft_free`) decomposes into the §1 tiers with **distinct evidence-node types** so a reviewer instantly sees the A3.1 node hangs on corpus evidence and the `hInv` node on fuzz (until T0.2 lands). Every residual is a tracked **defeater**. `docs/STATUS.md` is already trending this way — formalize it. Scope per-property (seL4 move): A5 applies only to `theft_free`, not the functional-correctness corollaries.

### Protocol layer (decompose to the layer that owns each property)
- **XOR split-secrecy (invariant #1) → a Lean information-theoretic lemma, NOT a symbolic model.** Computationally-sound Dolev-Yao XOR is **provably impossible** (Unruh, eprint 2010/389) — a symbolic verdict there would be *unsound*. Each half is marginally uniform iff the mask is uniform+independent: a trivial counting lemma in Lean, the layer you own.
- **FW-update domain separation → a Lean prefix-disjointness/injectivity lemma** over the fixed 75-B `PQFW_V1‖…` tag (needs only the tag prefix, not hash properties — SHA stays opaque). Same "decide it where it lives" logic as the on-device keccak-nesting fix.
- **Reserve Tamarin/ProVerif** for the tunnel/ordering/provisioning protocol only (PQ-relevant *by abstraction* as long as no algebraic equation is added — transfer-by-assumption, not a PQ theorem). CryptoVerif/PQ-Squirrel = overkill; they re-prove the protocol, never touch the Rust/Yul, and don't close A5.

## 3. Honest ceilings — what CANNOT be made ∀ (state as cited-TCB, never fake)

1. **A1 silicon + EVM precompile.** No verified hash covers the STM32 HASH peripheral *silicon* or the geth `0x02` precompile (geth uses Go stdlib `crypto/sha256`, unverified). On-chain A1 reduces to a *consensus/social fact*. T1.2 shrinks the *spec-transcription* part; the bytes-that-run stay KAT/consensus trust.
2. **keccak256 ≠ FIPS-202 SHA-3** (pad `0x01` vs `0x06` → different digests). **No verified implementation exists in any prover** for Ethereum's variant; it sits on the consensus-critical userOpHash/EIP-712/CREATE2 path. Flag as a residual *distinct from and weaker than* SHA-256.
3. **A5 is forever conditional on ITSR/SM-TCR/SM-DSPR/PRF conjectures for SHA-256** (ties A1). Even a fully-mechanized C10 EUF-CMA proof would be "secure *if* SHA-256 satisfies these." The mechanized bound is also classical-model; the post-quantum bit-security stays a hand argument (QROM).
4. **The multi-tool composition is human-glued.** There is no spanning theorem across protocol (Tamarin) ⊕ implementation (Lean/Aeneas) ⊕ bytecode (Halmos/Kontrol). Every interface is a documented assumption (SoK Computer-Aided Cryptography, eprint 2019/1393).
5. **Transcription/refinement TCB is relocated, never deleted** — only EVMYulLean-in-kernel (T2.1) collapses the EVM-side one into the kernel, and it's pre-release.
