# audit:gateway — Security Audit (20260623-220401)

Adversarial audit of the NS→Secure gateway: the firmware's #1 remotely-reachable
attack surface. A malicious USB companion / fully-compromised non-secure world
drives every `CMD_*` handler with maximally-hostile input. The hunt was for
memory-safety and parsing bugs yielding secret disclosure, an OOB write across
the secure/non-secure SRAM boundary, signature forgery, or an unlock/PIN bypass.

**Headline result:** I found **no CRITICAL, HIGH, or MEDIUM** confirmed-exploitable
vulnerability on the gateway parsing / memory-safety / dispatch surface. The
historically-vulnerable patterns (the `account_deployed` 4016-vs-8616 OOB; the
raw32 UserOp-forgery) are fixed and I could not construct an un-fixed sibling.
The primary deliverable is therefore the **enumeration ledger** (below) proving
that every handler's output length and every pointer-arithmetic site is bounded
by secure-side constants the companion cannot influence or single-fault-glitch.
Three LOW / informational defense-in-depth observations are recorded and
explicitly *not* inflated, per the rubric.

---

## Scope & threat model

**In scope (the gateway surface):**
- `secure/src/nsc/mod.rs` — dispatcher (QEMU mailbox + STM32U585 CMSE veneers), `gated_unlock`, `HandlerGuard`, the ship-blocker `compile_error!` fences.
- `secure/src/nsc/ptr_validate.rs`, `ns_ptr.rs` — NS pointer/length validation + `NsPtr<T>` typestate.
- `secure/src/nsc/state.rs` — `SecureState` singleton, `SLOT_CACHE`, `FW_UPDATE`, `SIGN_SNAP_BUF`.
- All `cmd_*.rs` handlers (sign_userop, sign_userop_batch, sign_offchain, offchain_status, offchain_sync, request_unlock, get_wallet_address, get_init_code, is_unlocked, lock, get_remaining, fw_begin/chunk/commit/status/abort, prodtest.rs).
- `trailer.rs`, `batch_trailers.rs`, `sig_wrapper.rs`, `factory_calldata.rs`.
- `secure/src/offchain_state.rs` (slot-key derivation + per-slot counter store), `secure/src/fw_update/{mod,staging}.rs` (chunk arithmetic), `secure/src/fi.rs` (the FI primitive everything gates on), `secure/src/hw/iwdg.rs` (the one veneer that stores an NS address).
- `proto/src/lib.rs` + `shared/src/lib.rs` — re-derived every wire format and bound from the code, not the doc.

**Threat model:** the entire non-secure world and the USB companion app are
fully attacker-controlled and send maximally-hostile input (arbitrary pointers,
lengths, flags, slot/account/chain selectors, malformed trailers). For the FI
angle, a profiled single-fault attacker (instruction-skip / stuck-at / value
clamp). Physical/SE-bus attacks are explicitly *out of this audit's scope*
(covered by the SE-tunnel / OPTIGA / measured-boot audits).

**Out of scope (tracked elsewhere):** display-layer WYSIWYS magnitude gaps
(`safe_refund_basegas_magnitude`, `safe_cow_gas_fee_pages_missing`) — these are
renderer findings already OPEN in project memory, not gateway-parsing bugs. The
SPHINCS+C10 verifier soundness, ZK circuits (retired), and Lean/Kontrol proofs.

## Methodology — what I read and how I hunted

1. **Foundation first.** Read the validation primitives end-to-end:
   `validate_ns_{read,write}_ptr` (constant-window + `checked_add` + mailbox
   exclusion + ARMv8-M `TT` per-32B block), the `NsPtr→ReadPtr/WritePtr`
   typestate, the `FihBool` pin-verified storage, and `fi::check_true_into_sentinel`
   / `OK_SENTINEL`. Everything downstream rests on these.
2. **Re-derived every wire format from `proto/src/lib.rs`** (offsets 0..330 for
   sign, the 17-byte off-chain header, the batch TLV format, all `*_LEN`
   constants) rather than trusting CLAUDE.md.
3. **Traced backward from every sink.** Enumerated all 30 `extern "cmse-nonsecure-entry"`
   veneers and every `core::ptr::write_volatile(out_ptr…)` / `copy_from_slice`
   into an NS buffer, then traced each backward to the length value that bounds
   it. (`grep` for the full sink list is reproduced in the ledger.)
4. **Differential analysis** of the symmetric paths: single-tx vs batch sign,
   deployed vs counterfactual off-chain (the resolved OOB template), `check_chunk`
   vs `write_chunk`, the early-vs-write-branch validation in `cmd_sign_offchain`.
5. **Enumerate-then-discharge** for the closed sets: every handler's unlock gate,
   every output-size decision, every length/offset field, every NS-write count.
6. **Red-teamed each "clean" verdict** — actively tried to break the precondition
   I was relying on (e.g. "could a multi-fault set both `emit_init_code` and
   `emit_type1`?", "could the idle-wipe race `&mut STATE`?", "could a torn
   `master_secret` read produce a *valid wrong* address?"). Counterexamples and
   why they failed are in the Self-review section.

## Findings (ordered by severity, most severe first)

### CRITICAL / HIGH / MEDIUM

**None.** No confirmed-exploitable gateway-parsing vulnerability of severity
MEDIUM or above was found. See the enumeration ledger for the discharge of the

### [LOW-1] `cmd_get_wallet_address` lacks the HIGH-7 `HandlerGuard` → `&mut STATE` data-race window with the SysTick idle-wipe

- **Location:** `secure/src/nsc/cmd_get_wallet_address.rs:43-113` (no `HandlerGuard::enter()` anywhere in the body); idle-wipe trigger at `secure/src/main.rs:3728` (`if timeout::is_idle() && nsc::is_unlocked() && !nsc::handler_is_busy()`); the racing writer is `nsc::zeroize_sensitive_state()` → `state::with_state(|s| s.zeroize_sensitive())` (`secure/src/nsc/state.rs:153-199`).
- **Vulnerability class:** Rust soundness / aliasing UB (overlapping `&mut STATE` borrows); inconsistent application of an existing FI/ISR-safety hardening.
- **Attacker & required capability:** Compromised companion that holds an unlocked session and lets the inactivity timer reach `TIMEOUT_TICKS` (120 s) while spamming `CMD_GET_WALLET_ADDRESS` for fresh `account_index` values (each does a ~1 s bootstrap C10 keygen and does **not** call `timeout::reset_activity()`).
- **Minimal trigger:** unlock; issue `CMD_GET_WALLET_ADDRESS(account_index = N)` for many never-cached `N` over a >120 s span with no button press; the idle-wipe SysTick tick lands while the handler is mid-`with_state`/mid-`peek_state`.
- **Exploitation path (and why it dead-ends):**
  1. Every other keygen/sign handler calls `super::HandlerGuard::enter()`, which makes `handler_is_busy()` true so the SysTick idle-wipe defers. `cmd_get_wallet_address` is the **only** keygen handler that does not (confirmed by per-handler grep in the ledger).
  2. With `handler_is_busy() == false`, if `is_idle() && is_unlocked()` becomes true on a tick during the ~1 s keygen, SysTick calls `zeroize_sensitive_state()`, which takes `&mut STATE` while the handler also borrows `STATE` (`peek_state(|s| s.master_secret)` at `:78`, `with_state(|s| s.bootstrap_cache_insert(...))` at `:108`). Overlapping `&mut` = UB by the language model; on the single-core Cortex-M33 it manifests as the ISR interleaving a wipe into the handler's read/write of the secret-holding singleton.
  3. **Why it does not reach any in-scope impact:** the only value this handler emits to NS is a **public** 20-byte CREATE2 address. A torn `master_secret` read (preempted mid-32-byte copy) makes `decrypt_entropy_blob` fail its **AES-GCM MAC**, so the handler returns `CryptoError` at `:95` *before* keygen and *before* any cache insert — it can never emit a *valid-but-wrong* address that could misdirect funds. A consistent read yields the correct address; the wipe then merely clears the (public, deterministic) `bootstrap_cache`. A torn `bootstrap_cache` entry holds only a public pubkey and is itself set to `None` by the wipe's `*entry = None`. No secret is written to NS, no signing occurs, and `pin_verified` is being driven *false* (not bypassed).
- **Invariant / property:** HIGH-7 ("SysTick refuses to wipe when depth > 0" / no aliasing-under-ISR on the secret-bearing singleton). It is the soundness contract that is violated, **not** invariant #4's secret confidentiality — no secret crosses to NS.
- **Evidence:**
  - `cmd_get_wallet_address.rs:78` `let master_secret … = Zeroizing::new(super::state::peek_state(|s| s.master_secret));` and `:108` `super::state::with_state(|s| s.bootstrap_cache_insert(...));` — both borrow `STATE` with no busy-guard held.
  - `main.rs:3728` `if timeout::is_idle() && nsc::is_unlocked() && !nsc::handler_is_busy() { nsc::zeroize_sensitive_state(); … }`.
  - Per-handler guard grep (ledger): every sign/offchain/get_init_code/fw_* handler shows `GUARD`; `cmd_get_wallet_address.rs` shows `-- none --`.
- **Falsification attempt:** I tried to turn the race into a fund-misdirection — get the handler to emit a *valid-looking wrong* address by tearing `master_secret`. It fails because the entropy blob is AES-GCM authenticated: a corrupted key fails the MAC and the handler bails with `CryptoError` before computing or caching any address. I also tried to make a torn cache entry persist with a wrong (account_index, pubkey) pairing for a later lookup; the wipe's unconditional `*entry = None` over the whole array clears any half-written entry, and a consistent read produces the correct, deterministic pubkey. No weaponizable outcome materialised.
- **Suggested fix (describe only):** add `let _busy = super::HandlerGuard::enter();` at the top of `cmd_get_wallet_address::run`, matching `cmd_get_init_code` and the sign handlers. (`cmd_get_remaining` and `cmd_lock` also touch `STATE` without a guard but their windows are sub-millisecond and/or idempotent — same class, even lower exposure; consider for consistency.)
- **Confidence:** confirmed (guard is missing; race window is real) — but confirmed **non-exploitable** for any in-scope impact.

### [LOW-2 / informational] No `compile_error!` fence forbids `prodtest` in a shipping wallet image

- **Location:** `secure/src/nsc/prodtest.rs` (NS-variable-count writes at `:394`, `:559`, etc.); `secure/src/main.rs:1289-1334` (prodtest replaces the wizard/unlock boot path); the fence block in `nsc/mod.rs:93-486` has no prodtest entry.
- **Vulnerability class:** build-process defense-in-depth (missing ship gate).
- **Why it is *not* a runtime finding:** the prodtest handlers themselves are clean — `cmd_usb_loopback_run` (`prodtest.rs:531`) and `cmd_trng_sample_run` (`:381`) bound `N` to `1..=256` and call `validate_ns_{read,write}_ptr(arg, N)` before any deref, and the fixed-size handlers validate their constant length. More importantly, `prodtest` is a *distinct factory firmware* that replaces `main()` with a USB command server and runs **before** the wallet is provisioned — there is no seed/entropy/PIN on a prodtest unit to steal. Shipping prodtest as the wallet firmware would be a gross build error that also produces an unprovisioned (valueless) device.
- **Suggested fix (describe only):** add a `#[cfg(all(feature = "mode-production", feature = "prodtest"))] compile_error!(…)` mirroring the existing `e2e-test` / `dev-testkey` ship gates, so the factory-only surface can never be additively compiled into a production image.
- **Confidence:** confirmed (no fence exists); informational (no provisioned secret at risk).

### [INFO] `slot_key_compute` truncates SHA-256 to 8 bytes (counter-store key)

- **Location:** `secure/src/offchain_state.rs:23-33` — `sha256(account_index‖chain_id_be‖slot_index_be)[..8]`.
- **Class / why benign:** an attacker controlling `(account_index∈0..=255, chain_id, slot_index∈22b)` could, with ~2³² work, find two tuples colliding in the 8-byte key, causing two logical slots to share a page-123 off-chain counter. This corrupts *firmware-local* gap/cap bookkeeping only; it cannot reuse a signing key, because (a) the signing key is derived independently from `(slot_master_entropy, chain_id, slot_index)`, and (b) the on-chain combined cap `slotUses[i] + offchainSigCount[i] < MAX_SLOT_USES` is the authoritative few-time-budget gate. No forgery, no fund theft. Needs-confirmation only as a robustness nit.
- **Confidence:** confirmed-benign for in-scope impact.

### [INFO] `register_ns_heartbeat` allows unrestricted re-registration

- **Location:** `secure/src/hw/iwdg.rs:176-187` (validates `addr` to NS-SRAM, 4-byte aligned; not one-time).
- **Class / why benign:** the stored NS address is read by the secure SysTick *only* for a liveness comparison (`hb != last`); the value is **never echoed to NS**, so it is not a secure-memory read-back primitive (and the validator confines it to NS SRAM anyway). An attacker re-registering it can at most defeat the USB-hang watchdog (point it at a constant → watchdog eventually fires → reset → SRAM zeroized = fail-safe; or point it at a fast counter → hung NS not auto-reset, recoverable by power-cycle). Neither is an in-scope impact.
- **Confidence:** confirmed-benign.

## Surfaces examined and judged clean (with the reason)

- **TOCTOU snapshot discipline.** Every handler validates the NS read pointer, then copies the whole input to a secure-side buffer (`SIGN_SNAP_BUF` in BSS, or a stack array) with byte-wise `read_volatile` *before* parsing. All subsequent parsing reads from the secure copy; NS is never re-read after validation (no validate-then-reread TOCTOU). The shared `SIGN_SNAP_BUF` is non-aliased because the dispatcher is single-threaded + non-reentrant and each handler's protocol-max is `const`-asserted ≤ `SIGN_SNAP_BUF_LEN`.
- **Output-size decisions.** All bounded by secure-side constants (ledger B). The one historically NS-influenced split (off-chain 4016/8616) is re-validated inside the write branch.
- **Unlock gating.** Every secret-touching handler reads `pin_verified` via the FI-hardened `FihBool::check_sentinel()` and compares against `OK_SENTINEL` (not a bare bool). `gated_unlock` itself is pre-commit-bumped, double-read, and sentinel-gated. No handler reaches the C10 signer or releases entropy with `pin_verified` false.
- **Read-back into secure memory.** `validate_ns_read_ptr` confines read pointers to NS SRAM / NS flash (constant window + `TT`), so a companion cannot aim a read at secure SRAM/flash; and no handler echoes input bytes from a companion pointer back out (the only echo, prodtest loopback, is N-bounded + dual-validated).
- **Confused-deputy on slot/account/chain/flags.** NS choosing these only selects *which* deterministic key signs and *which* counter is touched — this is invariant #8 by design. The signed digest and the trusted display are built from the *same* snapshotted fields, the on-chain `ownerIndex`/cap checks are authoritative, and the off-chain raw32/typed paths keccak-nest (disjoint from the bare `sphincsDigest`), so a chosen selector cannot forge or misdisplay.
- **`cmd_offchain_sync`.** "Set if greater" only; cannot lower a counter, so it can only *tighten* the few-time budget, never enable key reuse. Within the documented "host already drives slot use" trust model.
- **FW chunk arithmetic.** `check_chunk` enforces strict-monotonic `chunk_offset==received`, `offset+len ≤ expected_len`, and `expected_len ≤ SLOT_*_CAPACITY` (bounded at BEGIN); `write_chunk` re-guards every address with `checked_add`. Writes are confined to the inactive slot.
- **FW commit / signature.** `verify_manifest` runs the vendor C10 signature through `check_true_into_sentinel` (F-7); `verify_images` is ct_eq + drop-the-ctx-on-fail (resolved CRITICAL); OTP floor derives from the *signed* `fw_version`, never the unsigned snap field.
- **`fi.rs` primitive.** `OK_SENTINEL`/`FAIL_SENTINEL` are 32-bit Hamming-distant; `check_true_into_sentinel` double-evaluates with `wait_random` and a volatile commit; `read_volatile_voted` triple-reads. The whole gateway's fail-closed behaviour rests on this and it is sound.
- **`iwdg` heartbeat.** NS address validated to NS SRAM; the read value is used only for a liveness `!=` and never echoed.

## Self-review — counterexamples I went hunting for and why they failed

1. **"Multi-fault sets both `emit_init_code` and `emit_type1` → response overruns the validated buffer."** Failed: even with both set, the write is `8+4+4280+4+4128+4+4128 = 12556 = MAX_SIGN_RESPONSE_LEN` exactly. The validation reserves the *union* of init_code+type1+type2, so the worst conceivable flag state fills the validated buffer precisely — no overrun. (The flag mutual-exclusion is additionally FI-rechecked, so reaching that state needs ≥2 coordinated faults *and* still doesn't OOB.)
2. **"Single fault flips `account_deployed` true→false between the §4 gate and the §14 write → 8616-byte blob into a 4016-validated buffer."** Failed: the `else` (counterfactual) write branch re-runs `validate_ns_write_ptr(arg1, 8616)` through a sentinel *in the same branch* (`cmd_sign_offchain.rs:856`), so reaching the large write *requires* a passing large validation. This is exactly the resolved-OOB hardening; the sibling does not exist.
3. **"A torn `master_secret` during the `cmd_get_wallet_address` idle-wipe race yields a valid-but-wrong address → fund misdirection."** Failed: a corrupted key fails the entropy blob's AES-GCM MAC, so the handler returns `CryptoError` before computing or caching any address. The only outputs are `CryptoError` or the correct public address; no wrong-but-valid address can be emitted.
4. **"NS read pointer aimed into secure SRAM → leak a secret byte through a response."** Failed: `validate_ns_read_ptr`'s constant window excludes secure addresses on every target, and `TT` confirms NS classification per 32B block on hardware; no handler echoes companion-pointer bytes (except the N-bounded, dual-validated prodtest loopback on an unprovisioned factory unit).
5. **"`total_len` glitched larger after validation → snapshot read walks past the validated NS range / overruns `SIGN_SNAP_BUF`."** Failed: the same `total_len` local feeds the validation, the `snap_full[..total_len]` slice (which panics if `> buf len`), and the copy loop; a single glitch produces a panic at slice creation, not a silent OOB. There is no second, divergent length.
6. **"`cmd_offchain_sync` lowers a counter to re-enable key reuse past the few-time budget."** Failed: `last_userop_count_set` is monotonic set-if-greater; it can only raise the floor (tightening the cap), never lower it.
7. **"`batch_trailers` mis-routes a record so a secret-bearing slice is read OOB."** Failed: `parse_all` validates kind∈1..=8, per-kind length cap, `payload_start+len ≤ total_len`, aggregate `checked_add ≤ TRAILERS_TOTAL_MAX_LEN`, dup/mutual-exclusion, FI re-read of `(kind,tx_idx)`, and `walk==total_len` trailing-bytes — every slice `snap[start..start+len]` is provably in-bounds.
8. **"FW `chunk_offset` aimed at the FSBL / active slot / adjacent flash."** Failed: `chunk_offset==received` (starts 0, advances by verified len) + `offset+len ≤ expected_len ≤ SLOT_*_CAPACITY` + `checked_add` base — the address provably stays in the inactive slot, which BEGIN just erased.

## Open questions / items needing on-hardware confirmation

1. **[LOW-1] confirm the idle-wipe race is benign on silicon.** My argument that a torn `master_secret` always degrades to `CryptoError` (never a valid wrong address) relies on the entropy blob being AES-GCM authenticated and on the single-core ISR-interleave model. Worth a targeted test: hold an unlocked session, drive the idle timer to 120 s while spamming `CMD_GET_WALLET_ADDRESS`, and confirm the only observable outcomes are a correct address or `CryptoError` (never a stable wrong address). Independently, just add the `HandlerGuard` — it is a one-line consistency fix that closes the soundness gap regardless.
2. **[LOW-2] add the `prodtest` ↔ `mode-production` `compile_error!` fence** (mirrors the `e2e-test`/`dev-testkey` gates) so the factory-only surface can never be additively compiled into a shipping image. Confirm `make prod-check` would also catch a prodtest-bearing release set.
3. **QEMU vs hardware validator parity.** On QEMU `tt_range_is_ns` is a no-op (only the constant window gates). Production is `stm32u585` with `TT`, so this is not a production gap, but any future QEMU-only test transport that handles real secrets should not rely on `TT`. (No action for shipping firmware.)
4. **`slot_key_compute` 8-byte truncation** ([INFO]) — confirm the on-chain combined cap remains the sole authoritative few-time-budget gate (it is in the current contract), so a firmware-local counter collision can never widen the SPHINCS+ budget. No code change recommended unless the on-chain cap model changes.

### Bottom line

The NS→Secure gateway parsing / memory-safety / dispatch surface is, to my
analysis, **sound**: every NS pointer is validated before deref, every input is
snapshotted to secure memory before parse, every output write is bounded by a
secure-side constant the companion cannot influence or single-fault-glitch, every
secret-touching handler is unlock-gated through an FI-hardened sentinel, and the
two historically-exploited patterns (the off-chain OOB, the raw32 forgery) are
fixed with no surviving sibling. The only items worth a maintainer's attention
are the LOW-1 `HandlerGuard` consistency fix and the LOW-2 prodtest ship fence,
neither of which I could weaponize into an in-scope impact.
