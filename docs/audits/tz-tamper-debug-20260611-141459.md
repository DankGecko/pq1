# audit:tz-tamper — Security Audit (20260611-141459)

Auditor: adversarial TrustZone / tamper / production-gating review
Scope keys: invariant #4 (NS never reaches a secret or secure peripheral), tamper response, production debug-flag gating.

## Scope & threat model

In scope:
- SAU + GTZC1 (MPCBB SRAM, TZSC peripheral) isolation in `secure/src/sau.rs`.
- TAMP tamper monitoring/response in `secure/src/hw/tamp.rs` and the GTZC1 illegal-access controller `secure/src/hw/tzic.rs`.
- The power-consumption SCA mask `secure/src/hw/consumption_mask.rs`.
- Production-build `compile_error!` fences in `secure/src/nsc/mod.rs` and the feature definitions in `secure/Cargo.toml`.
- The CI / `prod-check` gate that CLAUDE.md and the feature docs claim enforces dev-flag exclusion.

Threat model (per engagement rules):
- The entire non-secure (NS) world and USB companion are attacker-controlled and send maximally hostile input.
- For physical surfaces: a patient attacker with the device, a logic analyzer, a CPA/EM probe, and the ability to glitch/desolder.
- "Production build" = `--release` image built for `stm32u585` and flashed to a shipping unit.

Headline result: **no CRITICAL or HIGH found.** The core secret-isolation boundary (invariant #4) is structurally sound — every secret-bearing peripheral and every secret-bearing SRAM/flash region is correctly walled off from NS, there is no NS-programmable DMA, and the AHB2 allowlist is silicon-validated. The findings are all **defense-in-depth / production-enforcement gaps**: the tamper and illegal-access responses are log-only with nothing forcing them to the wipe action in a shipping build, the documented CI/`prod-check` gate does not exist, and the SCA-mask timer the production fence *forces on* is left reachable from NS. Severities are MEDIUM and below, reported honestly rather than inflated.

## Methodology — what you read and how you hunted

1. Read the three primary subsystems end to end: `sau.rs` (SAU regions + GTZC1 MPCBB/TZSC), `hw/tamp.rs` (tamper), `hw/consumption_mask.rs` (SCA mask).
2. Read the full production-fence block and feature table: `nsc/mod.rs:78-338` and `secure/Cargo.toml` `[features]`.
3. Traced the boot/handler control flow in `main.rs` (GTZC init, `tamp::init`, `consumption_mask::init`, the `SysTick`/`DefaultHandler`/`PendSV` exception handlers) to see what is actually wired and what each tamper/violation path *does*.
4. Hunted the specific bypasses the mission named:
   - **NS-programmable DMA** → grepped the whole `secure/` tree for GPDMA/DMA usage.
   - **Secret peripheral left NS** → cross-checked the TZSC allowlist against the secret-bearing peripheral set.
   - **Secure SRAM/flash reachable by NS** → read both `memory-stm32u585.x` linker scripts and the MPCBB config; checked the flash secure-watermark story.
   - **Tamper log-only with no production wipe** → searched for every `trigger_lockout_wipe` definition/caller and confirmed which paths reach a wipe.
   - **Dev/test flag not fenced** → enumerated every dev/test feature and matched each against the fences; checked whether the documented `make prod-check` / CI exists.
5. Verified the fence keying could not be silently neutralized: checked `[profile.release]` for a `debug-assertions = true` override.

## Findings (ordered by severity, most severe first)

### [MEDIUM-1] Tamper and illegal-access response is structurally log-only, and no production build is forced to wipe/lock

> **STATUS: FIXED (2026-06-11).** TAMP now escalates to the shared intrusion wipe under a new `tamp-wipe` feature (`hw/tamp.rs` `poll`/`on_tamp_irq` → `hw::tzic::trigger_intrusion_wipe`, the renamed/generalized former `trigger_tzic_wipe`), and a `dual-se`-keyed ship-blocker `compile_error!` in `nsc/mod.rs` forces `tamp` + `tamp-wipe` + `tzic-wipe` ON for production. Bench safety preserved: with `tamp-wipe` OFF (the default, and for `e2e-test`/`dev-testkey` images) both handlers stay log-only. The two source-text pins in `hw_platform_under_test/pure_tests.rs` were rewritten to assert the escalation is feature-gated. Verified: host tests pass; ARM `cargo check` green for both-on / only-tzic / only-tamp / log-only; the fence fires for a clean `dual-se` production config.

- **Location:**
  - `secure/src/hw/tamp.rs:75-90` (`poll` — log + clear only), `:367-390` (`on_tamp_irq` — log + clear only), `:11-13` (module header: "Once hardware is stable end-to-end, flip to `trigger_lockout_wipe()`").
  - `secure/src/hw/tzic.rs:146-188` (`on_violation` — log + count; wipe is `#[cfg(feature = "tzic-wipe")]`), `:14-18` (doc: escalation lands "once TAMP has been moved off log-only").
  - `secure/src/main.rs:976-983` (`tamp::init`, log-only), `:3662-3663` (`SysTick` → `tamp::poll`), `:3724-3725` (`DefaultHandler` irqn 2 → `tamp::on_tamp_irq`), `:3731` (irqn 8 → `tzic::on_violation`).
  - `secure/Cargo.toml:226-236` (`tamp`/`tamp-irq` "**Does not change the trigger response** — the IRQ handler still logs + clears, never halts and never wipes"), `:237-250` (`tzic-wipe` "production CI must require this ON").
  - **Absence:** `secure/src/nsc/mod.rs` has force-on fences for `consumption-mask` (`:257-272`), `optiga-hw-counter` (`:205-222`), and `se050-derived-scp03` (`:291-312`), but **none for `tamp`, `tamp-irq`, or `tzic-wipe`**.

- **Vulnerability class:** Missing tamper response / unenforced production hardening (defense-in-depth gap on a physical/FI surface).

- **Attacker & required capability:** Physical attacker with the device and a fault-injection or bus/voltage-glitch rig.

- **Exploitation path (concrete):**
  1. Build the shipping image. `tamp` is **not** auto-composed by any mode and is **not** forced on by a fence, so a release `stm32u585` image can contain **zero tamper monitoring** — `tamp::init`/`poll`/`on_tamp_irq` all compile to no-ops (`tamp.rs:68-69`, `:88-90`).
  2. Even if `tamp` is enabled, the handler is hardcoded log-only: `poll` reads `TAMP_SR`, logs the reason, write-1-to-clears, returns (`tamp.rs:79-86`); `on_tamp_irq` does the same (`tamp.rs:379-389`). There is no `mode-production`-conditional that turns the response into a wipe — the `trigger_lockout_wipe()` the module header promises does not exist in `tamp.rs`.
  3. Mount a fault-injection campaign against the SAES/PKA/TRNG during key derivation or signing. ITAMP9 (crypto-peripheral fault — the FI canary, `tamp.rs:31-33`), ITAMP1 (voltage glitch), and ITAMP6 (SWD at RDP>0) fire, but the device merely logs and continues — the tamper tripwire that *should* zeroize SRAM secrets and brick the chip never does, so the attacker gets unbounded glitch attempts with no intrusion penalty.
  4. The sibling GTZC1 illegal-access path is the same shape: a detected NS→secure access raises IRQ 8 → `on_violation`, which only snapshots `SR` and bumps `VIOLATION_COUNT` (`tzic.rs:146-171`); the zeroize+arm+reset escalation is gated behind `tzic-wipe` (`tzic.rs:184-187`), which is default-off with no fence forcing it on. (The access itself is still hardware-blocked by GTZC, so this sibling is the *lower* half of the finding — only the intrusion *response* is missing, not the boundary.)

- **Invariant / security property broken:** The CLAUDE.md "Lifecycle" promises "zeroize on lock/tamper/brownout/inactivity" and lists tamper-driven wipe as part of the trust model; the TAMP/TZIC modules' own docstrings state the production response must be a wipe. A shipped device satisfies neither. This is the exact gap CLAUDE.md flags ("`tamp` … **log-only on this branch** — production must flip to `trigger_lockout_wipe()`") — confirmed **not closed and not enforced**.

- **Evidence:**
  ```rust
  // hw/tamp.rs:77-86  — the entire tamper "response"
  pub fn poll() {
      let sr = REG.tamp_sr.read();
      if sr & ITAMP_FLAG_MASK == 0 { return; }
      let _reason = reason_from_sr(sr);
      secure_log!("[TAMP] poll: {} (SR={:#010x})", _reason, sr);
      REG.tamp_scr.write(ITAMP_FLAG_MASK);   // clear and continue — no wipe
  }
  ```
  ```rust
  // hw/tzic.rs:184-187  — illegal-access escalation is opt-in only
  #[cfg(feature = "tzic-wipe")]
  unsafe { trigger_tzic_wipe(); }
  ```
  ```toml
  # secure/Cargo.toml:230-235 — tamp-irq explicitly keeps log-only semantics
  # **Does not change the trigger response** — the IRQ handler still logs + clears,
  # never halts and never wipes. Production hardening will flip the trigger
  # response separately ...
  ```
  Confirmed by grep: no `compile_error!` anywhere in `secure/src` mentions `tamp` or `tzic-wipe`.

- **Suggested fix (describe only):**
  1. Add a `compile_error!` fence in `nsc/mod.rs`, mirroring the `consumption-mask`/`optiga-hw-counter` pattern, that fails a `stm32u585 + !debug_assertions + !e2e-test + !dev-testkey` build unless `tamp` (and `tamp-irq`) and `tzic-wipe` are enabled.
  2. Make the TAMP response a wipe in production: have `poll`/`on_tamp_irq` call the same primitive `tzic::trigger_tzic_wipe`/`cmd_request_unlock::trigger_lockout_wipe` use (zeroize SRAM → `arm_wipe_flag` → `sys_reset`), gated so bench/`e2e-test`/`dev-testkey` builds keep log-only. Keep the IRQ-context constraints `trigger_tzic_wipe` already documents (no UI/I2C/semihosting from IRQ).
  3. Resolve the chicken-and-egg in the two docstrings (TZIC waits on TAMP, TAMP waits on "hardware stable") by landing both behind the one production fence.

- **Confidence:** confirmed (that production is *not* forced to wipe; the log-only behavior and absent fence are direct from source). The downstream FI-campaign benefit is the standard physical-access threat model.

### [MEDIUM-2] No CI / `prod-check` exists; dev-flag gating rests entirely on the release-build fences, whose `e2e-test` / `dev-testkey` escape hatches ship fixed secrets with no backstop

- **Location:**
  - `secure/src/nsc/mod.rs:93-134` — the main dev-feature fence, keyed on `feature="stm32u585", not(debug_assertions), not(feature="e2e-test"), not(feature="dev-testkey")`.
  - `secure/Cargo.toml:182-208` (`e2e-test` = fixed mnemonic + PIN + short-circuits every `confirm()`/`enter_pin()`), `:526-537` (`otp-hardcoded-master-key`), `:647-661` (`dev-testkey = ["otp-hardcoded-master-key"]`).
  - **Absences:** no `prod-check` target in the `Makefile` (only a stale comment at `Makefile:1633` "as part of `make prod-check`"); no `.github/workflows/` directory at all; `mode-production` (`secure/Cargo.toml:149`) is an empty alias used by **zero** build recipes.
  - Stale claims pointing at non-existent gates: `secure/Cargo.toml:533` ("Guarded … by a `compile_error!` in `secure/src/main.rs`" — that fence is actually in `nsc/mod.rs`, not `main.rs`), `:716-717` / `:80` (`make prod-check` "rejects any build"), CLAUDE.md "CI must gate".

- **Vulnerability class:** Production-build supply-chain / enforcement gap (documented compensating control does not exist).

- **Attacker & required capability:** The build/release operator (a mistake, not an external attacker). Impact if it slips is catastrophic, which is why the missing backstop matters.

- **Exploitation path (concrete):**
  1. The release fence at `nsc/mod.rs:93-134` *does* correctly reject `debug-log`, `mock-se`, `otp-hardcoded-master-key`, `ui-capture`, `ui-semihosting`, `ui-mirror`, `saes-self-test`, `uart-console`, `boot-pulse`, `bhk-hardcoded-master-key`, `sca-trigger`, `erc7730-dev-unattested`, `se050-rotate-scp03`, `se050-scp03-allow-factory-fallback` for a normal `--release` `stm32u585` build. Verified the keying is functional: `[profile.release]` in the root `Cargo.toml` sets `overflow-checks = true` but **not** `debug-assertions = true`, so `not(debug_assertions)` is true in release and the fence fires.
  2. But the fence is disabled whenever `e2e-test` **or** `dev-testkey` is set (`not(feature="e2e-test"), not(feature="dev-testkey")` preconditions). `e2e-test` provisions a fixed test mnemonic + PIN and short-circuits every secure-side `confirm()`/`enter_pin()` (`Cargo.toml:182-187`); `dev-testkey` makes the OTP master — and therefore the OPTIGA PBS / SE050 SCP03 roots — a shared compile-time constant (`Cargo.toml:647-660`). A release image built with either ships a **known seed/PIN** or a **shared pairing secret** and produces **no compile error**.
  3. The documented control that is supposed to catch this — "CI must gate" / `make prod-check` — **does not exist** (no workflow dir, no target). So the only thing standing between a fat-fingered `FEATURES=...,e2e-test` and a shipped wallet with a published seed is operator memory.
  4. Secondary keying dependency: the fence also evaporates for a non-`--release` (debug) build, since `debug_assertions` is then true. No tooling enforces "ship only `--release`".

- **Invariant / security property broken:** CLAUDE.md "Feature flags": "CI must gate shipped firmware on `debug-log` / `e2e-test` / `mock-se` / `otp-hardcoded-master-key` / `ui-capture` / OFF. The `compile_error!` fences … enforce most of this." The fences enforce the *non-escape-hatch* flags; the escape hatches and the build-profile assumption are enforced by a CI/`prod-check` that is absent.

- **Evidence:**
  ```rust
  // nsc/mod.rs:93-97 — escape hatches disable the whole dev-feature fence
  #[cfg(all(
      feature = "stm32u585",
      not(debug_assertions),
      not(feature = "e2e-test"),
      not(feature = "dev-testkey"),
      any( /* debug-log, mock-se, otp-hardcoded-master-key, ui-capture, ... */ )
  ))]
  compile_error!( ... );
  ```
  ```
  $ grep -rn "prod-check" Makefile        → only Makefile:1633 (a comment)
  $ ls .github/workflows/                 → (does not exist)
  $ grep -rn "mode-production" Makefile    → (no build recipe uses it)
  ```

- **Suggested fix (describe only):** The user has asked for **no `.github/workflows`** — so do *not* add a GitHub Actions gate. Instead:
  1. Add a real `make prod-check` target that attempts the shipping build and **fails** if it succeeds with any dev flag — e.g. a script that greps the resolved feature set (`cargo build --release ... --unit-graph` / `cargo metadata`) and hard-errors on `e2e-test`, `dev-testkey`, `mock-se`, `debug-log`, etc., and asserts the profile is `release`. Make the release/packaging targets depend on it.
  2. Tighten the fences so the escape hatches cannot *also* assert `mode-production`: add `compile_error!(mode-production + e2e-test)` and `compile_error!(mode-production + dev-testkey)` (siblings of the existing `mode-production + fw-rollback-e2e` fence at `nsc/mod.rs:178-183`), and have the actual ship recipe build with `mode-production` so those fences are live.
  3. Fix the stale comments (`Cargo.toml:533`, `:80`, `:716`) that point at a `main.rs` fence and a `prod-check` that don't exist — they create false confidence.

- **Confidence:** confirmed (absence of CI/`prod-check`, the escape-hatch holes, and the release-profile keying are all directly verified).

### [MEDIUM-3 / needs-confirmation] The SCA-mask timer (TIM2) that the production fence forces on is left out of the TZSC secure allowlist — NS can disable a mandated countermeasure

- **Location:**
  - `secure/src/hw/consumption_mask.rs:159-161` (driver targets TIM2 + GPIOA via the **secure** alias `0x5000_0000` / `0x5202_0000`), `:140` (`tim2_ccr1.write(duty)`), `:269` (`tim2_cr1.set_bits(CEN)`).
  - `secure/src/sau.rs:287` (`seccfgr1 = SECCFGR1_I2C1_BIT | SECCFGR1_I2C2_BIT` — APB1 allowlist is **only** I2C1 bit 13 + I2C2 bit 14; **TIM2 is APB1 bit 0, not set**), `:288` (`seccfgr2 = 0`).
  - `secure/src/nsc/mod.rs:257-272` — the fence that **forces `consumption-mask` on** for production.
  - For contrast, USB GPIO security *is* explicitly managed: `secure/src/hw/usb_hw.rs:130` marks PA11/PA12/PA15 NS; PA5 (the mask pin) is left at its GPIOA_SECCFGR reset default and never reconfigured.

- **Vulnerability class:** Side-channel countermeasure reachable/defeatable from the untrusted world (defense-in-depth gap).

- **Attacker & required capability:** NS/companion-controlled firmware **plus** a bench CPA/EM probe (physical). The NS half alone has no value; it only pays off for an attacker already capturing power traces.

- **Exploitation path (concrete):**
  1. Production firmware is forced to enable `consumption-mask` (`nsc/mod.rs:257-272`). It drives TIM2-CH1 PWM on PA5 and re-randomizes the duty every SysTick tick (`main.rs:3669-3670`).
  2. TIM2 is **not** in the TZSC secure allowlist (`sau.rs:287` sets only I2C1/I2C2 in SECCFGR1; SECCFGR2 = 0), so TIM2 keeps its NS reset attribution. The PA5 pin is a secure GPIO, but its waveform is generated by the NS-attributed timer.
  3. From the NS world, the attacker clears `TIM2_CR1.CEN` (or rewrites ARR/CCMR1) via the TIM2 NS alias. The PWM stops; PA5 freezes. The secure SysTick keeps writing `CCR1` but a stopped counter never reloads it, so the mask output is dead.
  4. The attacker now captures clean SPHINCS+C10 sign/keygen power traces with the mandated CPA countermeasure neutralized — recovering WOTS chain / FORS leaf secrets is back to the un-masked difficulty the fence was added to prevent (`nsc/mod.rs:248-256` states this is exactly the threat the fence defends).

- **Invariant / security property broken:** Invariant #4's spirit ("NS never controls a secure-world security mechanism") and the explicit production requirement that `consumption-mask` be active during the signing window. A countermeasure the build *cannot ship without* can be switched off by the threat actor it defends against.

- **Evidence:**
  ```rust
  // sau.rs:287-288 — APB1 secure set is just the two SE buses; TIM2 (bit 0) absent
  let seccfgr1 = SECCFGR1_I2C1_BIT | SECCFGR1_I2C2_BIT;  // bits 13,14
  let seccfgr2: u32 = 0;                                  // "nothing security-critical in APB2 today"
  ```
  ```rust
  // hw/consumption_mask.rs:160-161 — secure-alias target, but TZSC leaves TIM2 NS
  // TIM2 — secure alias at 0x5000_0000.
  ```

- **Suggested fix (describe only):** Add the TIM2 bit to `SECCFGR1` in `sau.rs` (and the matching TZIC IER mask) so TIM2 is secure-attributed, consistent with the driver already using the secure alias. Confirm PA5's GPIOA_SECCFGR bit is secure (it appears to be, by reset default, but make it explicit alongside the USB-pin config in `usb_hw.rs`). Re-run `make gtzc-enforcement-hw` to confirm TIM2 RAZ-faults on NS access without breaking the mask.

- **Confidence:** needs-confirmation. The allowlist omission and the forced-on fence are certain; the *exploitability* depends on the exact STM32U5 GTZC semantics for an NS-attributed timer driving a secure AF pin (whether NS can write TIM2 at all under the current SAU region-3 NS peripheral window — which it can, `sau.rs:378` — and whether the secure SysTick re-write fully compensates). The omission should be fixed regardless; it is the only secure-world driver whose peripheral is not in the allowlist.

### [LOW / needs-confirmation] GTZC2 (TAMP / backup domain) is entirely unconfigured; NS reachability of the tamper controller is unproven

- **Location:** `secure/src/sau.rs:284-286` ("TAMP lives in GTZC2 (a different controller); its SECCFGR setup is owed in a follow-up"), `:331-334` (SECCFGR4 left at NS reset default, IER mask 0). No GTZC2/`RTC_SECCFGR`/`TAMP_SECCFGR` security write exists anywhere (grep-confirmed). The BHK feature stores key bytes in the TAMP backup registers and protects them with `TAMP_SECCFGR.BHKLOCK` (`secure/src/hw/bhk.rs:89-91`, `:322-324`).

- **Vulnerability class:** Backup-domain security attribution left to reset defaults (defense-in-depth gap).

- **Attacker & required capability:** NS/companion-controlled firmware.

- **Exploitation path (concrete, contingent):**
  1. The firmware never assigns a security attribute to TAMP / the RTC backup domain (only GTZC1 is configured). The TAMP NS alias falls inside SAU NS region 3 (`0x4000_0000–0x4FFF_FFFF`, `sau.rs:378`), so NS can *form* the address.
  2. **If** the STM32U5 backup domain defaults NS-accessible with TZEN=1 (needs RM/silicon confirmation), NS could write `TAMP_CR1 = 0` and disable all internal-tamper detection — silently removing the monitoring in MEDIUM-1 from the untrusted side.
  3. The BHK key bytes themselves stay protected: `BHKLOCK` (`bhk.rs:322-324`) makes the backup registers readable only by SAES, not by any CPU access, and BHK provisioning runs in the secure world before NS starts. So this is a tamper-monitoring/availability concern, not a key-extraction path.

- **Invariant / security property broken:** Invariant #4 (NS must not reach a secure peripheral) — *if* the reset default is NS-accessible. Currently unproven.

- **Evidence:** `sau.rs:284-286` explicitly defers the GTZC2/TAMP security config; no code configures it.

- **Suggested fix (describe only):** Configure GTZC2_TZSC (and `TAMP_SECCFGR`/`RTC_SECCFGR` privilege/secure bits) to mark TAMP and the backup domain secure during boot, mirroring the GTZC1 allowlist, and extend the TZIC arm to GTZC2's illegal-access lines. Validate NS RAZ-fault on the TAMP NS alias on real silicon.

- **Confidence:** needs-confirmation (depends on the STM32U5 TZEN=1 backup-domain reset default, which I could not establish from the codebase alone).

## Surfaces examined and judged clean (with the reason each is safe)

- **AHB2 crypto block (AES, HASH, RNG, PKA, SAES) + I2C1/I2C2 — SECURE.** `sau.rs:287-296` sets the correct SECCFGR1/SECCFGR3 bits; CLAUDE.md records `make gtzc-enforcement-hw` PASSED on real silicon (7/7 RAZ-fault on NS access). No secret-bearing peripheral is left NS. **Clean.**
- **NS-programmable DMA → S-SRAM / secure peripheral.** Grep of the entire `secure/` tree shows **no GPDMA/DMA configuration at all** — the only references are comments noting Trezor uses a GPDMA linked-list for the consumption mask and this firmware deliberately does **not** (`consumption_mask.rs:13-27`), and `spi_hw.rs:224` noting a path "needs DMA" (i.e. is polled). USB OTG FS is FIFO/PIO, not a system-bus DMA master. With no firmware GPDMA setup, channels stay at the TZEN=1 secure reset default, so NS cannot program a DMA master to read secure SRAM. **Clean.**
- **Secure vs NS SRAM split.** `memory-stm32u585.x` puts *all* secure data/stack in SRAM1 (192 KB, S alias `0x30000000`); `nonsecure/memory-stm32u585.x` puts NS in SRAM2 (64 KB, `0x20030000`). MPCBB1 marks SRAM1 all-secure, MPCBB2 marks SRAM2 all-NS (`sau.rs:246-256`); SAU region 2 marks only the SRAM2 NS-alias window NS (`sau.rs:375`), so SRAM1's NS alias is SAU-secure too (double-protected). SRAM3 is used by neither world (so its un-configured MPCBB3, at the secure reset default, holds nothing). **Clean.**
- **Secure flash.** Bank 1 is fully covered by the SECWM1 secure watermark (`memory-stm32u585.x:11`); NS can only reach the FLASH NS control bank (`NSCR`) which the watermark confines to bank 2, and the secure register bank (`SECCR`, secure alias `0x5002_2000`) is SAU-secure so NS faults on it (`hw/flash.rs:846-847`, `hw/otp.rs:91-93`). PBS / admin-wipe / counter pages live in bank 1. **Clean.**
- **USB OTG FS left NS.** Intended (`sau.rs:215-220`): the NS HID transport drives DWC2 directly; OTG is FIFO-based with no system-DMA master, and the D+/D-/related GPIOs are explicitly marked NS (`usb_hw.rs:130-131`) while everything secret stays behind the CMSE veneers (which validate NS pointers and copy to S-stack). NS reaches exactly its own FIFO + NS SRAM. **Clean.**
- **SAU region map.** Regions 0 (NS flash bank 2), 1 (NSC veneers), 2 (NS SRAM2), 3 (NS peripheral NS-alias window) are correct; everything in the `0x5xxxxxxx` secure-alias space is SAU-secure by default, so every secure driver address (RNG `0x520C_0800`, GPIOA `0x5202_0000`, GTZC `0x5003_xxxx`, TAMP/RCC/PWR `0x5600_xxxx`/`0x5602_xxxx`) is NS-unreachable. **Clean.**
- **Release-fence keying.** `[profile.release]` does not set `debug-assertions = true`, so the `not(debug_assertions)` fences in `nsc/mod.rs` actually fire for shipping `--release` builds. The non-escape-hatch dev flags (`debug-log`, `mock-se`, `otp-hardcoded-master-key`, `ui-capture`, etc.) **are** caught. **Mechanism sound** (the gap is the escape hatches + missing CI, MEDIUM-2).
- **OPTIGA S-1/S-2/S-3 fences (mission asked to verify).** S-3 (`optiga-hw-counter` mandatory) fence exists at `nsc/mod.rs:205-222`; S-2 (`optiga-reset-oids` must not ship) at `:229-243`; the related SE-tunnel ship-blockers (`se050-derived-scp03` HIGH-1, `optiga-no-shield` MEDIUM-1) at `:291-312` / `:322-338`. **S-1 is an AC/metadata fix (F1D0 `Change=Auto`), not a feature flag — it has no `compile_error!` fence and remains an open bring-up ship-blocker**, consistent with CLAUDE.md (acceptable only because nothing has shipped). Noted, not a new finding.

## Open questions / items needing on-hardware confirmation

1. **STM32U5 backup-domain reset default (LOW finding).** With TZEN=1 and GTZC2/`TAMP_SECCFGR` unconfigured, is the TAMP NS alias actually NS-accessible? If yes, NS can disable tamper monitoring. Confirm by probing a write to `TAMP_CR1` via the NS alias from the NS world and checking it takes effect (or RAZ-faults).
2. **TIM2 NS-access semantics (MEDIUM-3).** Confirm on silicon whether NS can stop TIM2 (clear `CEN`) while PA5 is a secure AF pin, and whether the secure per-tick `CCR1` write compensates. Easiest check: from NS, clear `TIM2_CR1.CEN`, then scope PA5 during a sign and confirm the mask is dead.
3. **`iwdg` not forced on in production.** The USB-hang watchdog is optional and unfenced; a shipping build without it loses the hang-detect reset. Availability/DoS hardening only — flagged for completeness, not a secret-exposure path.
