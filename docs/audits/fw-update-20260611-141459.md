# audit:fw-update — Security Audit (20260611-141459)

Auditor: adversarial firmware-update review (read-only).
Verdict: **No in-scope CRITICAL/HIGH/MEDIUM vulnerability found.** The
signature/rollback/staging/boot chain is well-hardened against the stated
threat. One sub-MEDIUM invariant deviation is reported ([LOW-1]). One
**high-confidence functional brick** (rollback off-by-one) is documented in
Open Questions — it is *not* one of the in-scope security impacts (its
direction is anti-downgrade-safe), but it is severe and almost certainly a
ship blocker, so it is surfaced for your decision.

## Resolution (patched in this commit)

Both items below were fixed after the audit:

- **Open-Question #1 (rollback brick) — FIXED.** `cmd_fw_commit.rs` now bumps
  the OTP floor to `new_version.saturating_sub(1)` (a new `new_rollback_floor`
  local) instead of `fw_version`. The floor is derived from the **signed**
  `fw_version`, *not* the unsigned `boot_counter_snap` (which a hostile
  companion could lower at BEGIN to re-open a downgrade window). `verify_rollback`
  keeps its strict `>` everywhere. After installing V the floor is V−1, so
  FSBL boots V (`V > V−1`) while every release `≤ V−1` stays rejected.
  `boot_state.last_good_version` still records the true installed version V.
  Regression guard added in `negative_commit_bumps_otp_before_writing_new_manifest`.
- **[LOW-1] — FIXED.** `cmd_fw_status.rs` and `cmd_fw_abort.rs` now gate on
  `pin_verified` (sentinel pattern) like BEGIN/CHUNK/COMMIT, matching
  CLAUDE.md "PIN unlock required on every call" for CMDs 20–24. Not a wedge:
  a session context exists only after a PIN-verified BEGIN, and lock/idle-wipe
  already drops `FW_UPDATE`, so a locked device has nothing to probe or abort.
  The two pure-tests that previously pinned the *absence* of the gate were
  flipped to assert its presence.

Verification: 71 FW-update pure tests + 76 `fw-manifest` tests pass; the secure
crate compiles clean for `thumbv8m.main-none-eabi` (`stm32u585`). The strict
anti-downgrade direction is unchanged — the fix only stops the device bricking
on a legit update.

## Scope & threat model

In scope: the firmware-update streaming path —
`secure/src/fw_update/{mod,staging,verify,vendor_pubkey}.rs`,
`secure/src/nsc/cmd_fw_{begin,chunk,commit,status,abort}.rs`,
`fw-manifest/`, `fwsign/` (read-only, format only),
`secure/src/hw/{otp,boot_state,flash}.rs`, and the FSBL boot-select/verify
(`fsbl/src/{main,verify,slot,otp}.rs`).

Threat model (per engagement): the entire non-secure world and the USB
companion are fully attacker-controlled and send maximally hostile input.
The PIN-unlock gate means a fund/secret attack must occur while the device
is unlocked (user has entered the PIN). Physical attackers may glitch
(fault-injection) or desolder. Target impacts only: fund theft, seed/key
extraction, PIN/unlock bypass, signature forgery, WYSIWYS violation.

Out of scope as *findings* (but noted where adjacent): pure availability /
self-DoS that needs a valid vendor signature or only bricks the device
without exposing a secret; FSBL internals beyond boot-select; the
trusted-display/button path itself (separate `wysiwys-clearsign` audit) —
this audit assumes `ui::confirm::confirm()` is genuinely button-gated and
NS cannot inject confirms.

## Methodology — what I read and how I hunted

I traced data and control flow end-to-end against the mission's hunt list:

1. **Signature/manifest-verify bypass.** Read the full verify chain
   (`fw_update::verify_manifest`, `fw-manifest::ManifestRef::verify_*`),
   checked the order of "compute-all-then-enforce-in-order" and the
   FI-sentinel around the SPHINCS+C10 verify; confirmed the signature is
   over a *stored* `manifest_digest` field that `verify_digest` independently
   re-derives and enforces; confirmed COMMIT re-hashes the actually-flashed
   bytes (`verify::verify_images`) against the signed hashes; confirmed FSBL
   re-runs the whole chain + re-hashes on every boot.
2. **Version rollback.** Read `otp.rs` (`rollback_floor`, `bump_to`, the
   one-way QW program), `verify_rollback`, the COMMIT bump, the FSBL floor
   read, the `fw_rollback_e2e` harness, and `fwsign`'s `boot_counter_snap`
   logic. Reasoned about every reset-window between OTP bump / manifest
   write / boot-state write.
3. **Staging state-machine abuse.** Walked `check_chunk` (monotonic-append,
   overlap, oversize, zero-length, overflow) and `staging::write_chunk`
   (QW alignment, final-short-chunk, `checked_add`), and the flash backstop
   `write_slot_quadword_verified` / slot geometry / capacities.
4. **Partial/interrupted update.** Walked BEGIN's erase order, COMMIT's
   write order, and FSBL's `pick_slot` try-once/`TRIED`/`COMMITTING` logic.
5. **PIN gate on every command.** Checked each of the 5 handlers.
6. **Preimage confusion.** Checked the 75-byte domain-tagged preimage and
   confirmed the vendor signing key is structurally distinct from the
   wallet master/slot keys.
7. Cross-checked the production `compile_error!` fences in `nsc/mod.rs`,
   the `FW_UPDATE` zeroize-on-wipe, and verified no `reset*`/`increaseMax*`
   veneer exists for OTP or boot-state.

## Findings (ordered by severity, most severe first)

### [LOW-1] `CMD_FW_STATUS` and `CMD_FW_ABORT` skip the PIN-verified gate (documented-invariant deviation)

- **Location:** `secure/src/nsc/cmd_fw_status.rs:20-68` (handler body — no
  `pin_verified` check); `secure/src/nsc/cmd_fw_abort.rs:18-30` (handler
  body — no `pin_verified` check). Contrast the gated siblings
  `cmd_fw_begin.rs:199`, `cmd_fw_chunk.rs:39`, `cmd_fw_commit.rs:33`, each
  of which opens with
  `if peek_state(|s| s.pin_verified.check_sentinel()) != crate::fi::OK_SENTINEL { return NotInitialized }`.
- **Vulnerability class:** access-control / invariant deviation
  (defense-in-depth gap).
- **Attacker & required capability:** any code in the attacker-controlled
  NS world / USB companion, with **no PIN**, at any time (the CMSE veneers
  `nsc_fw_status` / `nsc_fw_abort` at `nsc/mod.rs:1340-1353` are always
  callable).
- **Exploitation path:**
  1. NS calls `CMD_FW_STATUS` with a valid NS output pointer. The handler
     validates the pointer (FI-hardened) and writes
     `[state | recv_secure | recv_nonsecure | slot]` regardless of unlock
     state. This leaks whether an update session is live and how many
     bytes have been streamed.
  2. NS calls `CMD_FW_ABORT`. The handler unconditionally sets
     `FW_UPDATE = None`, dropping any in-flight (PIN-authorized) streaming
     context.
- **Invariant / security property broken:** CLAUDE.md gateway table —
  "20–24 FW_BEGIN/CHUNK/COMMIT/STATUS/ABORT … **PIN unlock required on
  every call**" — and the module contract in `fw_update/mod.rs:11-15`
  ("**Unlock required.** Every entry point checks `pin_verified` first.").
  Both are violated for STATUS and ABORT.
- **Evidence:**
  ```rust
  // cmd_fw_status.rs — run() begins directly with the pointer check,
  // NO pin_verified gate:
  pub(super) unsafe fn run(args: &GatewayArgs) -> u32 {
      let out_ptr = args.arg1;
      let write_ptr_ok = crate::fi::check_true_into_sentinel(|| {
          validate_ns_write_ptr(out_ptr, FW_STATUS_RESPONSE_LEN)
      });
      ...
  ```
  ```rust
  // cmd_fw_abort.rs — run() does only this, NO pin_verified gate:
  pub(super) unsafe fn run() -> u32 {
      unsafe { *core::ptr::addr_of_mut!(FW_UPDATE) = None; }
      NscStatus::Ok as u32
  }
  ```
- **Why it does NOT rise to MEDIUM (no in-scope impact):**
  - STATUS leaks only **non-secret** progress metadata (state ∈ {idle,
    receiving, staged}, two byte counters, slot index 0/1). It reveals
    nothing the existing `CMD_IS_UNLOCKED` (11) doesn't already, no PIN,
    no entropy, no key, no derived secret. `FW_UPDATE` is non-`None` only
    after a PIN-verified BEGIN and is wiped on lock/idle (see Surfaces),
    so STATUS does not even leak post-lock session state on HW.
  - ABORT only clears in-RAM context. `FW_UPDATE` is non-`None` only after
    a PIN-verified BEGIN, and the attacker who can call ABORT already owns
    the transport — it can equally just stop forwarding chunks or corrupt
    the stream. No new capability; the dropped `FwUpdateCtx` is inline in a
    `static` (no heap), so the unguarded drop is a benign double-zeroize at
    worst, not a use-after-free.
  - Neither path can install firmware, bypass unlock, forge a signature,
    or violate WYSIWYS.
- **Suggested fix (describe only):** add the same
  `peek_state(|s| s.pin_verified.check_sentinel()) != OK_SENTINEL →
  NotInitialized` gate to the top of both handlers, matching
  BEGIN/CHUNK/COMMIT, so the code matches the stated invariant. (ABORT can
  keep its no-`HandlerGuard` design; only the PIN check needs adding.)
- **Confidence:** confirmed (deviation is real); needs-confirmation only on
  the *impact* ceiling — I could not construct any higher-severity exploit
  and do not believe one exists.

## Surfaces examined and judged clean (with the reason each is safe)

- **Signature chain / no flash-before-verify.** `verify_manifest`
  (`fw_update/mod.rs:379-453`) computes structural/CRC/digest/vendor-fpr
  results, runs the SPHINCS+C10 verify through `fi::check_true_into_sentinel`
  (double-eval, hamming-distant sentinel, ~2-fault bar), then enforces in
  documented order via `?` (`s_err? … d_err? … if sig != OK_SENTINEL …
  r_err?`). The signature is over the **stored** `manifest_digest` field
  (`lib.rs:430-445`), but `verify_digest` (`lib.rs:413-424`) independently
  recomputes `SHA256("PQFW_V1"‖ver‖secure_hash‖nonsecure_hash)` and is
  enforced *before* the signature gate, so the signed value provably binds
  `(version, secure_hash, nonsecure_hash)`. BEGIN runs this **before** any
  destructive flash op (`cmd_fw_begin.rs:240` precedes the erase at `:313`).
  No flash-before-verify; no unsigned field is authority-bearing.
- **Image binds the flashed bytes.** `verify::verify_images`
  (`verify.rs:40-72`) requires `received_* == m.secure_len()/nonsecure_len()`,
  re-reads the inactive slot through a `read_volatile` loop, and compares
  the fresh hash to both the streaming hash and `m.secure_hash()/
  nonsecure_hash()`. The image lengths are unsigned, but SHA-256 binds the
  exact byte sequence *and* its length, so shrinking/growing the declared
  length cannot collide to the signed hash (second-preimage). FSBL repeats
  this on every boot (`fsbl/src/verify.rs:22-49`), so a torn / partial
  stream fails the hash and is rejected — a partial update is **never
  bootable**.
- **Rollback direction is sound (anti-downgrade holds).** `verify_rollback`
  requires strict `fw_version > floor` (`lib.rs:474-480`); the OTP floor is
  a one-way unary tally (`otp.rs:235-332`, bits only 1→0, no reset path);
  BEGIN reads the floor and rejects `version ≤ floor` before any flash op.
  An attacker cannot install a signed *older* release (it is rejected at
  BEGIN and again by FSBL). The COMMIT bump is monotonic. (The *magnitude*
  of the bump is wrong — see Open Questions — but only in the over-strict
  direction.)
- **Staging state machine.** `check_chunk` (`mod.rs:457-494`) enforces
  strict monotonic append (`chunk_offset == received`, so no gaps / no
  overlaps / no re-transmit), `chunk_len ≤ FW_MAX_CHUNK` (1024),
  `chunk_offset + chunk_len ≤ expected_len`, and `expected_len ≤
  SLOT_*_CAPACITY` (bounded at BEGIN, `cmd_fw_begin.rs:265-272`). Zero-length
  chunks are a harmless no-op; CHUNK-after-COMMIT is impossible (COMMIT
  nulls `FW_UPDATE` then resets); a stale/failed BEGIN never replaces a good
  context (the `FW_UPDATE` write is the last step, after verify+confirm+
  erase). The write address stays inside `[slot_base, slot_base+capacity)`,
  and `SLOT_SECURE_CAPACITY` (0x74000) lands exactly at the next slot/region
  boundary for both A and B (`flash.rs:900-922`).
- **OOB / arithmetic.** Both `check_chunk` and `write_chunk` use
  `checked_add`; the CHUNK handler bounds `total_len` and `data_len`
  against fixed `[u8; FW_MAX_CHUNK]` / `[u8; FW_CHUNK_HEADER_LEN]` buffers
  (`cmd_fw_chunk.rs:46-83`); STATUS writes exactly `FW_STATUS_RESPONSE_LEN`
  (=10) bytes with offsets 0/1/5/9 all in-bounds (`proto/src/lib.rs:740-744`).
  The NS manifest/chunk snapshots are copied byte-wise (`read_volatile`)
  into secure-stack buffers after FI-hardened `validate_ns_read_ptr`, so
  there is no TOCTOU on the verified bytes.
- **PIN gate on the destructive handlers.** BEGIN/CHUNK/COMMIT each gate on
  `pin_verified` via the sentinel pattern before touching flash/OTP. The
  glitch-defense failure counter only advances inside a PIN-verified BEGIN.
- **Preimage confusion.** The signed preimage is domain-tagged
  (`DOMAIN_TAG = b"PQFW_V1"`, `lib.rs:107-115`) and verified with the
  **vendor** key (`VENDOR_PK_SEED/ROOT`, baked from `FSBL_VENDOR_PUBKEY` at
  build), which is a distinct SPHINCS+C10 keypair from the wallet
  master/slot keys (BIP-39 derived). The on-chain/off-chain wallet digests
  are signed by *different keys entirely*, so even a structural collision
  would not transfer — a firmware signature can never be a wallet signature
  or vice-versa.
- **No reset / increase-max veneer.** Grep confirms no
  `reset_rollback`/`reset_boot`/`increase_max` path exists in firmware
  (only tests asserting their absence). Invariant #7's "no reset path"
  holds for the FW surface too.
- **Production fences.** `nsc/mod.rs:115-195` `compile_error!`-fences
  `debug-log`/`e2e-test`(implied)/`mock-se`/`otp-hardcoded-master-key`/…
  and specifically `fw-rollback-e2e` and `fwup-transport-e2e` out of
  `mode-production`. `confirm_install`'s `e2e-test` auto-true
  (`fw_update/mod.rs:86-90`) and COMMIT's `fwup-transport-e2e`
  pre-OTP short-circuit (`cmd_fw_commit.rs:77-87`) therefore cannot reach a
  shipping image.
- **`FW_UPDATE` zeroize.** Idle-wipe drops the context (ZeroizeOnDrop wipes
  the 8 KB manifest + hashers) under `#[cfg(stm32u585)]`
  (`nsc/state.rs:187-198`); COMMIT and ABORT also null it.
- **COMMIT trusts an immutable in-SRAM manifest.** COMMIT does not re-run
  the *signature* check (only `verify_images`), but `ctx.manifest_bytes`
  is a secure-SRAM snapshot taken at BEGIN (after the signature passed) and
  is never mutated by CHUNK; NS cannot touch secure SRAM. So COMMIT acting
  on the BEGIN-verified manifest is sound. (Doc nit: `mod.rs:25-29` claims
  the signature is "verified twice" — it is verified once at BEGIN; the
  images are re-verified at COMMIT. Harmless inaccuracy, no exploit.)

## Open questions / items needing on-hardware confirmation

1. **FUNCTIONAL BRICK — OTP rollback off-by-one (high confidence; NOT an
   in-scope security impact, but very likely a ship blocker).**
   COMMIT bumps the OTP floor to the firmware **version** instead of to the
   intended `version - 1`:
   `cmd_fw_commit.rs:92` `let new_version = manifest.fw_version();` →
   `:105` `otp::bump_to(new_version)`. Because `verify_rollback` requires
   strict `fw_version > floor` (`fw-manifest/src/lib.rs:475`), after a
   COMMIT of version V the floor becomes V, and on the **next boot** FSBL's
   `verify_rollback(floor=V)` rejects the just-installed slot (`V > V` is
   false, `fsbl/src/main.rs:136`); the old slot (version < V) is also
   rejected; `pick_slot` returns `None` and FSBL `halt()`s
   (`fsbl/src/main.rs:94-95`). On an RDP-2 production unit (no SWD) this is
   a **permanent brick on the first OTA update**.
   - The intended floor is clearly `V - 1`: `fwsign` computes
     `boot_counter_snap = version - 1` and explicitly *rejects*
     `snap == version` because it "would freeze the OTP floor at the
     current version, making future updates require snap >= version"
     (`fwsign/src/subcommands/sign.rs:118-127`, test
     `negative_resolve_snap_equal_to_version_rejected`). But
     `boot_counter_snap` is **never read** by COMMIT or FSBL — the commit
     path uses `fw_version` instead, i.e. exactly the `snap == version`
     foot-gun fwsign guards against. The `fw_rollback_e2e` harness even
     documents the same off-by-one in prose ("floor 2 = 'v2 has already
     been committed'", "v2 @ floor2 reinstall -> REJECT",
     `secure/src/fw_rollback_e2e.rs:131-137`).
   - Why this is NOT a security finding: the error is in the **over-strict**
     direction — it never *accepts* a downgrade, only rejects too much. It
     needs a *valid vendor-signed* update and a *user confirm* to trigger,
     so it is not attacker-leverageable, and no secret is exposed (funds
     restore from the 24-word seed on another device). It is pure
     availability.
   - Why it is untested: the only full-cycle harnesses either use the floor
     as a function argument with no OTP burn (`fw_rollback_e2e`) or
     short-circuit COMMIT *before* the OTP bump + reboot
     (`fwup-transport-e2e`, `cmd_fw_commit.rs:77-87`). The
     bump→reboot→FSBL-reject path is explicitly called out as unproven in
     `fw_rollback_e2e.rs:12-18`.
   - Suggested fix (describe only): bump to `manifest.boot_counter_snap()`
     (= V-1) rather than `manifest.fw_version()`, **keeping** the strict
     `>` in `verify_rollback` (do not relax it to `>=`, which would let a
     reinstall of the current version pass but is a needless widening).
     Validate `boot_counter_snap < fw_version` on-device first (it is
     unsigned). Confirm on a sacrificial board: BEGIN→CHUNK→COMMIT a real
     v(N+1), power-cycle, assert FSBL boots the new slot and the OTP floor
     reads N.

2. **`write_chunk`'s "independently safe" comment overstates the
   guarantee (latent, not live).** `staging.rs:20-22` claims the
   `checked_*` arithmetic means a future direct caller "cannot overflow into
   adjacent flash." It can: `write_chunk` has **no** `offset+len ≤
   expected_len` bound of its own (only the final-short-chunk equality
   check), and the backstop `write_slot_quadword_verified`
   (`flash.rs:1181-1191`) permits **the entire secure bank**
   `0x0C00_0000..0x0C10_0000` — which includes the PIN-attempts page 124,
   the admin/wipe-flag page 125, the boot-state page 6, and the FSBL pages.
   Today the only caller (`cmd_fw_chunk.rs:108`) always runs `check_chunk`
   first, so the live path is bounded and safe. Recommend either tightening
   the backstop to the specific slot extent or adding the `expected_len`
   bound inside `write_chunk`, and correcting the comment, so the claim is
   not load-bearing for a future maintainer. (Needs-confirmation that no
   second caller exists — grep shows none today.)

3. **Companion-triggerable glitch-defense wipe = DoS during an unlock
   window (availability, not in target list).** 5 in-RAM (or 20
   flash-lifetime) rejected BEGINs arm the admin wipe + reset
   (`cmd_fw_begin.rs:48-156, 246, 250, 270`). A malicious companion present
   during *any* unlock window (e.g. while the user unlocked to sign) can
   send 5 garbage manifests and force a full wallet wipe (factory-reset +
   re-enter-seed). It destroys on-device state but cannot extract anything,
   and funds restore from seed — so it is griefing, not theft. Flagging
   because the PIN gate is the only thing bounding it and the threshold (5)
   is low; consider whether a confirmed-bad-signature flood should wipe, or
   only count toward a softer rate-limit.

4. **NS-image fingerprint is not shown at the install confirm
   (defense-in-depth gap vs CI-key compromise).** `confirm_install`
   displays the **secure** image fingerprint + vendor-key fingerprint +
   version (`fw_update/mod.rs:104-110`) but not the **nonsecure** image
   fingerprint. A vendor/CI-key-compromise that swaps *only* the NS image
   (secure unchanged) would not change any on-screen word. This requires
   vendor-key compromise (out of the NS threat model) and the NS world is
   untrusted anyway (no secrets, everything re-validated at the NSC
   gateway), so impact is bounded — but the fingerprint defense is
   advertised as catching exactly CI-key compromise, and it is blind to NS.

5. **`FW_UPDATE` is not zeroized on idle-wipe under non-`stm32u585`
   builds.** The wipe in `nsc/state.rs:194-197` is `#[cfg(stm32u585)]`-gated.
   Production is `stm32u585`, so this is QEMU-only; noting for completeness.

---

### One-line disposition

The firmware-update path resists the in-scope threats (no verify bypass, no
downgrade, no partial-boot, no OOB, no preimage confusion, PIN-gated
destructive ops). Fix [LOW-1] for invariant hygiene; treat Open-Question #1
(rollback brick) as a functional ship blocker even though it is not a
security-target impact.
